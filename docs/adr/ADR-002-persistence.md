# ADR-002: Persistence — embedded H2 by default, PostgreSQL optional

- **Status:** Accepted
- **Date:** 2026-08-12
- **Deciders:** Service Atlas build agent
- **Related requirements:** §6 data model, FR-1.3, FR-4.3, Q-5

## Context

Service Atlas is local-first (§1). A user points it at a folder of repositories and explores the
result on their own machine; there is no multi-user story in v1 (§1.3). Persistence therefore
needs to:

- require **zero setup** — no server to install before the first scan;
- survive restarts, so a workspace and its scan history are still there tomorrow (FR-1.3, FR-4.3);
- still be credible for a shared/team deployment later, without a schema fork;
- keep startup inside the 5-second budget in Q-5.

## Decision

**Embedded H2 in file mode is the default datastore. PostgreSQL is available via a Spring profile.
Both run the identical Flyway migration set.**

- Default JDBC URL: `jdbc:h2:file:${service-atlas.data-dir}/atlas;AUTO_SERVER=TRUE`, where
  `data-dir` defaults to `${user.home}/.service-atlas`. The database file lives outside the repo.
- `--spring.profiles.active=postgres` switches to PostgreSQL via `SPRING_DATASOURCE_*`
  environment variables. Nothing else changes.
- Flyway owns the schema. `db/migration` is **shared** by both databases — no
  `db/migration/{h2,postgresql}` split.
- To keep one migration set valid on both engines, the DDL sticks to a portable subset:
  - `VARCHAR`, `TIMESTAMP`, `BIGINT`, `CLOB`/`TEXT` avoided in favour of `VARCHAR` +
    dedicated large-text columns typed as `CLOB` only where H2 and Postgres agree;
  - JSON payloads are stored as text columns (`*_json`), not as `jsonb` — the application
    serialises and deserialises them. We never query inside them in SQL.
  - identity columns declared as `BIGINT GENERATED BY DEFAULT AS IDENTITY`, supported by both.
  - no engine-specific functions in defaults; timestamps are set by the application.
- JPA is configured with `ddl-auto: validate`. Hibernate never creates or alters a table; a drift
  between entity and migration is a startup failure, not a silent schema change.

## Consequences

**Positive**

- `./gradlew bootRun` works on a clean machine with no database installed — the zero-config goal.
- The `.atlas` bundle (FR-1.4) is a portable export, so "move my workspace" does not mean
  "move a database file", and H2's single-file storage stays an implementation detail.
- Testcontainers runs the real Postgres migration path in CI, so the "identical schema" claim is
  tested rather than asserted.

**Negative**

- The portable-DDL subset costs us `jsonb` indexing and engine-specific niceties. Acceptable:
  the JSON columns are payloads, never query predicates.
- H2 file mode is single-process. `AUTO_SERVER=TRUE` softens this (a second process can attach),
  but two concurrent Service Atlas instances on one data dir is not a supported configuration.
- H2 has occasionally broken storage-format compatibility across major versions. Mitigated by
  pinning the H2 version in the build and by treating `.atlas` bundles — not the H2 file — as the
  durable, portable representation of a workspace.

## Alternatives rejected

- **SQLite** — a natural local-first fit, but the JVM drivers are JNI-based (packaging friction
  for a single `bootJar`) and the dialect gap to Postgres is much wider than H2's.
- **Plain JSON files on disk** — trivially portable, but scan versioning (FR-4.3), overlay merge
  (FR-4.4) and concurrent scan progress writes all want transactions.
- **PostgreSQL required** — rejected outright: it violates zero-config.
